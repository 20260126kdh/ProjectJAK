# 코딩 규칙

## 기본 원칙

- C#과 Unity 기존 관례를 따르고, 주변 코드의 줄바꿈과 명명 스타일을 유지한다.
- 기능 수정과 무관한 포맷 정리나 리팩터링을 한 변경에 섞지 않는다.
- 한 클래스가 이미 맡고 있는 책임은 가능한 한 유지하고 새 전역 매니저를 쉽게 추가하지 않는다.
- 데이터, 게임 로직, 화면 표현을 분리한다.

## Unity 직렬화와 Inspector

- Inspector 연결이 필요한 필드는 `[SerializeField] private`를 기본으로 한다.
- 런타임 전용 값은 불필요하게 직렬화하지 않는다.
- 직렬화 필드 이름 변경 시 기존 씬과 프리팹 데이터 유실을 막기 위해 `FormerlySerializedAs`를 검토한다.
- `GetComponent` 반복 호출은 초기화 시 캐시하되, 기존 생명주기와 동적 생성 흐름을 먼저 확인한다.
- Inspector 미연결 가능성이 있으면 조용히 실패하지 말고 프로젝트의 기존 로그 형식에 맞춰 명확히 알린다.

## 데이터

- 재사용하는 정적 데이터는 ScriptableObject 또는 기존 CSV 파이프라인을 사용한다.
- 런타임 변경이 필요한 ScriptableObject는 원본을 직접 수정하지 않고 복제한다.
- ID, enum, CSV 문자열은 저장 데이터와 연결될 수 있으므로 변경 영향을 검색한다.
- 밸런스 수치를 코드에 새로 하드코딩하기 전에 이미 Inspector/데이터 필드가 있는지 확인한다.

## 명명과 문서화

- 타입과 공개 멤버는 PascalCase, private 필드와 지역 변수는 camelCase를 사용한다.
- bool은 의미가 드러나는 `is`, `has`, `can`, `should` 계열 이름을 우선한다.
- 공개 타입과 공개 메서드에 한국어 XML 주석을 작성한다.
- 매개변수와 반환 의미가 자명하지 않으면 `<param>`, `<returns>`를 작성한다.
- 주석은 규칙, 순서 의존성, 예외 처리 이유를 설명한다.

## 오류 처리와 로그

- Inspector 필수 참조 누락, 잘못된 데이터, 불가능한 상태는 조기에 검사한다.
- 복구 불가능한 설정 오류는 `Debug.LogError`, 기능을 건너뛸 수 있는 조건은 `Debug.LogWarning`을 사용한다.
- 로그 앞에는 기존 방식처럼 `[ClassName]` 문맥을 붙인다.
- 매 프레임 반복되는 경고를 만들지 않는다.

## 변경 전 점검

- 참조 검색으로 호출부, Inspector 필드, enum/CSV/저장 연계를 확인한다.
- 외부 패키지와 생성 파일인지 확인한다.
- 씬이나 프리팹 수정이 필요한지, 코드 변경만으로 끝나는지 구분한다.

## 완료 기준

- 컴파일 오류가 없다.
- 정상 경로와 대표적인 실패/경계 조건을 확인한다.
- Inspector 변경 사항과 수동 테스트 절차가 기록되어 있다.
- 시스템 규칙이 바뀌었다면 관련 Docs 문서가 함께 갱신되어 있다.
